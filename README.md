# CarRent

A peer-to-peer car rental marketplace app built with Flutter + Firebase.
Any registered user can browse/rent cars **and** list their own — there is
no separate owner/renter account type.

## Status

**All 10 phases complete.** Phases 7 and 8 landed around the same time
from two parallel sessions on this project. Phase 7: Maps & GPS tracking,
via OpenStreetMap instead of Google Maps (see below) — pickup-location map
on Car Details, an interactive pin picker in Post Car, and live

## Image hosting: Cloudinary, not Firebase Storage

Firebase Storage now requires the paid **Blaze** plan even for free-tier
quota. To stay on Spark, image uploads (profile photos, and car photos in
Phase 4) go through **Cloudinary's** free tier instead via a plain HTTP
multipart upload — see `lib/core/services/cloudinary_image_upload_service.dart`.

Before running the app, fill in your real values in
`lib/core/constants/cloudinary_config.dart`:

1. Sign up free at [cloudinary.com](https://cloudinary.com).
2. Copy your **Cloud name** from the Dashboard.
3. Settings → Upload → Upload presets → **Add upload preset** → Signing
   Mode = **Unsigned** → save, and note its name.
4. Put both values into `CloudinaryConfig.cloudName` and
   `CloudinaryConfig.unsignedUploadPreset`.

All image-uploading code depends on the abstract `ImageUploadService`
interface (`lib/core/services/image_upload_service.dart`), not on
Cloudinary directly — if this project ever moves to the Blaze plan, swap in
a Firebase-Storage-backed implementation there and change one line in
`main.dart`.

## Firestore security rules

`firestore.rules` is deployed and grows feature-by-feature (Section 26 of
the spec). Currently covers:
- `users/{uid}` — any signed-in user can read, only the owner can write.
- `cars/{carId}` — any signed-in user can read; only the claimed owner can
  create, and only the actual owner (`resource.data.ownerId`) can update/delete.
  (Covers Phase 4's publish/edit/delete/disable — no rule changes needed
  since Phase 3 already wrote these forward-looking.)
- `favorites/{uid}` — only that user can read/write their own doc.
- `bookings/{bookingId}` — readable only by the two parties on it. Creating
  one requires being the named renter, for a real car whose stored owner
  matches. Updates may only touch the `status` field, and only along exact
  transitions: owner accepts/rejects a pending request, owner starts a
  confirmed rental (→ active), owner confirms return (→ completed), renter
  cancels a pending or confirmed request. Everything else is denied.
- `bookingLocations/{bookingId}` — the renter's **latest** position only
  (one doc per booking, overwritten each update; no history). Writable only
  by the booking's renter, only while it's `active`, and only once they've
  granted consent (`locationConsent == 'granted'` on the booking). Readable
  **only by the booking's owner**, only while it's `active`. Deletable only
  in a write that moves the booking out of `active` (`getAfter()`), which is
  how `requestReturn`/`completeRental` remove it atomically. All checks read
  the booking doc via `bookingDoc()`, never the location doc's own fields.
- The renter may set `locationConsent`/`locationConsentAt` on their own
  active booking (server-stamped time, a decline can later become a grant).
- `reviews/{bookingId}` (Phase 8) — doc id *is* the booking id, so a second
  submission for the same booking hits the `allow update: if false` guard
  instead of double-writing. Creating one requires being the renter on a
  `completed` booking matching the claimed car/owner/renter, rating 1-5.
  Reviews are immutable once posted.
- `cars/{carId}` and `users/{userId}` updates (Phase 8) also allow a
  narrow carve-out beyond the owner/self check above: any signed-in user
  may bump `rating`+`reviewCount` by exactly one step (`isRatingBump()` in
  `firestore.rules`) — this is what lets a renter's review roll into the
  car's and owner's aggregate rating. It can't verify the *average math* is
  correct, only that the shape of the change looks like one review being
  added — see "Known simplification (Phase 8)" below. **Phase 10 fix**:
  before this pass, the owner's own "self" branch on both `cars` and
  `users` had no field lock, so an owner could directly overwrite their own
  `rating`/`reviewCount` (bypassing the review system entirely), and
  neither `create` rule stopped a brand-new listing/account from starting
  with a fake rating already set. Both are closed now — `create` requires
  `rating == 0 && reviewCount == 0`, and self-updates may not touch either
  field (only `isRatingBump` can).
- `notifications/{notificationId}` (Phase 9) — any signed-in user may
  *create* one for any recipient (there's no server trigger to hand this to
  instead — no Cloud Functions, see "Notifications: in-app only" below),
  but only the recipient can read it, and the only update ever allowed is
  the recipient toggling their own `read` field. See "Known simplification
  (Phase 9)" below for what this trade-off actually means.

Composite indexes are also deployed (`firestore.indexes.json`): `cars` by
`status`+`createdAt` (Home), `cars` by `ownerId`+`createdAt` (My Cars),
`bookings` by `renterId`+`createdAt` and `bookings` by `ownerId`+`createdAt`
(Booking hub), `reviews` by `carId`+`createdAt` and `renterId`+`createdAt` (Car
Details' Reviews section and My Reviews), and `notifications` by
`userId`+`createdAt` (Notifications screen) — Firestore needs these
because each query combines an equality filter with `orderBy` on a
different field.

Redeploy after editing with:

```
firebase deploy --only firestore:rules,firestore:indexes --project=carrent-app-86916
```

## Maps: OpenStreetMap, not Google Maps

Google Maps Platform requires a **billing-enabled** Google Cloud project
even though it ships a monthly free credit — the same situation as Firebase
Storage/Blaze (Phase 2). To stay off billing entirely, Phase 7 uses
**OpenStreetMap** tiles via `flutter_map` + `latlong2` instead — no API key,
no card on file. See `lib/widgets/osm_map_view.dart` (`OsmMapView` +
`MapPins`), used in three places:

- **Car Details** — a static pin at the car's declared pickup point.
- **Post Car's Location step** — tap the map to place/move the pin
  (flutter_map has no built-in draggable-marker gesture, so tap-to-relocate
  stands in for "drag the marker"); paired with the GPS-capture flow from
  Phase 4 (`geolocator` + `geocoding`, still used for "Use Current
  Location").
- **Active Rental screen** — the car's last reported position during an
  active rental (see GPS tracking below).

OSM's tile usage requires attribution, which `OsmMapView` always renders
(`RichAttributionWidget`) — don't remove it.

**Every map embedded in a scrollable page is `interactive: false`.** All
three spots above sit inside a `ListView`/`SingleChildScrollView`, and an
interactive map there fights the page's own scroll gesture — a scroll that
starts over the map gets partly consumed as a pinch/pan instead of
scrolling the page (reported directly: "when I scroll... the map gets
zoomed"). Since `flutter_map`'s tap detection runs independently of its
pan/zoom interaction flags, Post Car's tap-to-place-pin still works fine
with `interactive: false`. Car Details and the Active Rental screen each
pair their static map with a small expand button that opens
`FullScreenMapScreen` — full pinch-zoom/pan there, since that page isn't
inside anything scrollable. **If you add another map anywhere in this app,
default it to non-interactive and give it the same expand-button escape
hatch rather than making it interactive in place.**

## GPS tracking during an active rental (Section 17-18)

`lib/core/services/tracking_service.dart` drives this, separate from
Phase 4's one-shot `LocationService`.

- **Consent**: the first time the renter opens an active booking, a dialog
  asks whether to share their location with the owner (what, who, how
  often, until when). The answer is saved on the booking as
  `locationConsent` (`granted`/`declined`) + server-stamped
  `locationConsentAt`. Nothing is sent without a grant — enforced by the
  rules, not just the UI. A renter who declined can opt in later from the
  same screen.
- **Sharing**: once granted, the renter's device sends its latest position
  every 45 s (`TrackingConfig.heartbeatInterval`) to
  `bookingLocations/{bookingId}`, overwriting the previous one — a steady
  heartbeat even while parked, so the owner can tell "parked" from
  "offline". The switch *pauses* sending; it doesn't withdraw consent.
- **Owner view**: a live listener on that one document drives the map, with
  "updated X ago · accurate to ~N m", and an out-of-date warning after 2
  minutes without an update (`TrackingConfig.staleAfter`).
- **Ending**: leaving `active` — the renter's "I've returned the car"
  (`return_requested`) or the owner's Confirm Return — deletes the
  location in the same batch as the status change, the rules stop
  accepting writes/serving reads for that booking, and the renter's app
  stops its GPS stream. The old append-only `carLocations` history was
  deleted when this replaced it.

**Known limitation**: tracking only runs while the renter has the Active
Rental screen open in the foreground — there's no background service or
foreground notification keeping it alive if they switch apps or lock their
phone. True always-on tracking would need an Android foreground service and
an iOS background-location entitlement, a meaningfully bigger lift than
this phase's scope.

## Platform commission (15%)

Every new booking stores three amounts, computed once in
`BookingService.createBooking` via `PlatformPricing.split`
(`lib/core/constants/pricing.dart`): `totalPrice` (what the renter pays),
`commissionAmount` (15%, rounded to satang) and `ownerPayout` (the rest —
the two always add up to the total exactly). Amounts, not the rate, are
stored, so a future rate change never rewrites existing bookings.

- Renters only ever see `totalPrice`.
- Owners see `ownerPayout` everywhere (their booking cards, the Bookings
  "Earned" stat, the active rental screen), with the full breakdown —
  renter pays / platform fee / your payout — on Booking details only.
- Bookings made before commission existed have neither field and count
  as no fee: the owner's payout is the full total. Nothing is deducted
  retroactively.
- `firestore.rules` (`isValidBookingPricing`) checks on creation that the
  total is days x the car's current daily price and that the commission and
  payout match it (±0.01 for rounding). Changing the rate means updating
  both the constant and the rule.

This is display/tracking only — no real payment splitting. **Known
limitation**: the split is computed on the renter's device and stored on the
booking document, so it's hidden in the app's UI but visible to anyone who
inspects that document in Firestore directly. Truly hiding it would need a
server (Cloud Functions, i.e. the Blaze plan) — the same client-only trade-off
as VIN verification.

## VIN verification (Post Car)

Post Car's **Car info** step has an optional **VIN** field. When the owner
leaves it (or presses Next), `VinDecoderService`
(`lib/core/services/vin_decoder_service.dart`) decodes it with NHTSA's free
vPIC API (`DecodeVinValues`, no key; CORS-enabled, so it also works on web),
called directly from the client with an 8 s timeout.

- Make / model / year are auto-filled — only into fields that are empty or
  still hold an earlier auto-fill — and stay editable.
- `verified`: vPIC `ErrorCode` is exactly `0` and make, model and year are all
  present. `partial` (data but an error, e.g. a bad check digit) pre-fills
  with a warning. Anything else — malformed VIN, no data, network error,
  timeout — shows "VIN could not be verified" and never blocks the listing.
- Stored on the listing as `vin` (uppercased, or `''`) and `vinVerified`.
  `vinVerified` is true only if the decode was clean **and** brand/model/year
  still match it at save time. The app shows a "VIN verified" badge, never
  the VIN itself.
- vPIC only covers US-market vehicles; most Thai-market VINs return no data,
  so those listings are simply unverified.

**Trust boundary**: with no backend (Cloud Functions need the Blaze plan),
`vinVerified` is set by the owner's own client. Firestore rules check its
type but can't re-run the decode, so a modified client could claim a false
verification. It's a trust signal, not a guarantee — the same accepted
client-only trade-off as the review rating aggregates.

## Notifications: in-app only, no push (Phase 9)

Actually delivering a push notification to a device needs a server-side
component — normally a Cloud Function triggered on a Firestore write,
calling the FCM Admin SDK. Cloud Functions need the paid **Blaze** plan,
the same wall as Storage and Maps (usage would almost certainly stay $0 at
this scale, but it needs a card on file). There's also no secure way to
send real pushes straight from client code — the credential that lets you
send to any device must never ship inside the app.

Given the choice, this project skips real push delivery and builds a
complete **in-app notification center** instead: `lib/core/services/
notification_service.dart` writes a Firestore document the moment an event
actually happens client-side (booking created/accepted/rejected/cancelled,
rental completed, new review — see `BookingService`/`ReviewService`), and
the Notifications screen + Home's bell badge read it back. This satisfies
Section 15's "store in Firestore for history" requirement fully; it just
doesn't wake a closed app. Two notification types from the spec's list —
"rental starting soon" / "ending soon" — are also skipped: those are
time-based reminders, not event-driven, and without a scheduled server job
there's no reliable way to fire one when nobody has the app open.

## Known simplification (Phase 9)

`notifications` create rule allows *any signed-in user* to write a
notification for *any* recipient — there's no server standing between the
event and the write to attribute it properly, so the rule can only check
"is this a signed-in user," not "is this app code doing what it's supposed
to." A malicious client could spam another user's notification feed with
fake messages. Same class of trade-off as Phase 5's booking-overlap check
and Phase 8's rating bump: closing it for real needs a Cloud Function (or
Blaze) standing between the client and the write.

## Known simplification (Phase 6)

Completing a rental always sets the car's status back to `available`, even
if the owner had disabled the listing before the booking was confirmed —
there's no tracking of "what it was before it became rented." Edge case,
not expected to come up often; revisit if it does.

## Known simplification (Phase 8)

Rolling a review's rating into the car's and owner's denormalized
`rating`/`reviewCount` averages happens client-side inside a Firestore
transaction, then has to get past a security rule (`isRatingBump()` in
`firestore.rules`) that lets *any* signed-in user touch someone else's
`cars`/`users` doc — but only the `rating`/`reviewCount` fields, and only
one review's worth of increment at a time. Firestore rules have no way to
look at the review document being written in the same request and confirm
the new average was computed correctly from it — they can only bound the
*shape* of the change (exactly those two fields, count up by exactly one,
rating in range), not prove the arithmetic. A client that wanted to lie
could still nudge a rating within one review's worth of noise per write.
Same class of trade-off as Phase 5's booking-overlap check: avoiding Cloud
Functions (which need the paid Blaze plan, same reason Storage and Google
Maps were skipped) means some validation that would be trivial server-side
is instead "as tight as rules alone can make it." Acceptable for this
project's stakes; would need a Cloud Function (or Blaze) to close for real.

## Phase 10 (Polishing) — what actually changed

A pass across error handling, loading/empty states, security rules,
performance, animations, and tests — not a rewrite, a set of concrete
fixes:

- **Security**: see "Phase 10 fix" above — closed the self-rating gap on
  `cars`/`users`. This is the one item in this pass with a real correctness
  payoff; everything else here is UX/DX polish.
- **Performance**: every network image in the app (car photos, avatars) now
  goes through one shared `lib/widgets/cached_image.dart` backed by
  `cached_network_image`, replacing ad hoc `Image.network` + placeholder/
  error boilerplate that was duplicated slightly differently across 8
  files. Disk caching means scrolling back to an already-seen car card (or
  reopening a screen) doesn't refetch its image. Also found and fixed
  `ReviewCard` opening two separate Firestore listeners for the same
  reviewer document (one for the avatar, one for the name) — now one.
- **Animations**: a `Hero` transition (tag `car_image_${car.id}`) carries a
  car's cover photo from its card (Home/Favorites/My Cars) into Car
  Details' image carousel — the one animation in the spec's "smooth
  animations where appropriate" that had an obvious, high-payoff spot.
- **Error/empty states**: `FavoritesScreen` and Car Details' Reviews
  section could show "no favorites"/"no reviews" on a genuine fetch
  *error*, not just when the list was actually empty — both now check
  `snapshot.hasError` first, matching the pattern already used everywhere
  else (Home, Booking, My Cars, My Reviews, Notifications).
- **Tests**: went from 1 widget test to 24, adding unit tests for the pure
  logic that doesn't need Firebase mocking — `CarDraft`'s five per-step
  validation gates, `CarFilters`, `AppFormatters` — plus widget tests for
  the shared `LoadingWidget`/`ErrorStateWidget`/`EmptyStateWidget`. Full
  integration tests (real screens against live/mocked Firebase) are still
  out of scope — most screens now depend on live `AuthService`/`CarService`/
  etc., which `flutter test`'s fake platform can't provide without mocking
  packages like `firebase_auth_mocks`/`fake_cloud_firestore` wired in, a
  bigger investment than this pass.

What Phase 10 deliberately did *not* do: rewrite the "known simplification"
trade-offs from Phases 5/6/8/9 (booking-overlap race window, rating-bump
shape-only validation, notification spam surface) — those all trace back
to the same root cause (no Cloud Functions/Blaze), documented above rather
than worked around, and closing them for real is a Blaze-plan decision, not
a code change.
